## 2026-09-20 恢复日志写放大及检查点优化

新增并发快照回归：在较旧 IndexedDB 快照写入期间注入 100 次约 3 KiB 工作区修改，使内存中的同步尾日志超过 256 KiB。旧代码会在快照完成后把超大尾日志再同步写回 Storage；现在 `flush()` 在写回前复核预算，保留“现场尚未受保护”提示并继续写入最新状态，直到快照追上提交，再清除日志。测试确认从未发生超预算 `setItem`，并用全新 RecoveryService 从数据库恢复出最后一笔修改和相同 revision。

`TerminalModel` 原本每个输出块都把从基础屏幕开始的整个累计 `outputJournal` 重新写入恢复日志。现增加 `terminal-output` 增量操作，每条只保存新解析的序号与输出；状态应用器会校验检查点基线、序号连续、事件数和字节上限。现有含 `baseSequence/outputJournal` 的快照继续可读。xterm完整屏幕序列化仍有可测成本，因此在每次输出仍同步提交、ACK仍等待本地保护的前提下，将输出日志上限从 64 KiB 调至 128 KiB，事件数仍最多128条；额外恢复回放量小于约49 KiB原始输出。

验证：`cd web && npm test` 10个测试文件49/49通过；`npm run check` 与 `npm run build`通过。真实HTTPS/WSS双节点场景 `actual WSS Protobuf PTY input, alternate screen, refresh and moving retain one session` 1/1（17.6秒）通过，刷新和移窗仍挂载同一会话且没有重放PTY输入。fake-indexeddb额外覆盖并发超预算追赶、旧检查点增量追加、序号冲突和128 KiB上限拒绝。

实际 65 秒诊断样本（`BLORA_PERF_DIAGNOSTICS=1`，用于比较写入，不计验收）中，同步恢复日志 `setItem` 写入累计字符从此前约156,756,017降至24,212,427，调用数2,631次、累计耗时0.566秒、单次最大55,630字符/2.2ms；差异由输出日志改存增量造成。启用诊断时p95为47.8ms，最大90.1ms、3/3607长帧；观察器会扰动交互采样。
