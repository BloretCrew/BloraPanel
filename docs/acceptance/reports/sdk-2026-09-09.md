# 独立扩展 SDK 验证

`sdk/` 提供版本化 `AppManifest`、窗口/标签入口、现场捕获/恢复和能力门禁；`createSandboxHost` 在每次调用前检查扩展声明的能力，宿主传输仍需在服务端重新校验用户、节点、资源和任务权限。`examples/reference-app` 使用 `file:` 依赖独立构建，不修改 `web/` 桌面核心。

验证命令：

```sh
make sdk
```

结果：SDK 与参考扩展均通过 clean `npm ci`、TypeScript 检查和构建；`npm run package` 生成可复现的 `reference.blora-extension.json` 独立包。前端 AppHost 新增 `registerExternalApp` 与 `loadExternalApp` 合同，对外部清单执行 protected/权限/版本校验后再注册；新增 `internal/extensions` 本地受控注册源管理器，并接入 Master 的管理员 API（`/api/v1/extensions`、`/extensions/install-package`、`/{id}/manifest`）及默认扩展管理窗口；已安装启用扩展的 manifest 可由普通登录用户读取，安装/包体/管理仍限管理员。窗口支持选择本地包、计算 SHA-256 并提交安装。执行清单/Host API/能力白名单/SHA-256 校验，配置 `--extensions-public-key` 后强制 Ed25519 签名校验，升级拒绝降级且要求三段数字版本，升级保存旧包体/清单并在写入失败时恢复包体，提供管理员包体读取与回滚接口；清单与包体以临时文件加 rename 持久化。扩展用户数据目录在卸载时默认保留，显式 `cleanup=true` 才清理。真实 TLS 集成测试验证安装、独立包安装、列表、包体读取、普通用户 manifest 读取和管理拒绝；生命周期与篡改/越权/无签名/降级/数据保留失败测试通过。宿主动态 bundle 加载、opaque sandbox 和任务桥接已接入；版本迁移、资源标签跨设备迁移及跨设备工作区副本仍未完成，E06/E07 仍不能标记完成。
扩展管理前端 Playwright 场景 `web/tests/browser/extensions.spec.ts` 验证管理员对已安装扩展执行禁用、回滚、卸载时的完整请求边界，并断言禁用请求体；命令 `npm run test:e2e -- --workers=1 --trace=off --grep 'extension management installs' --reporter=line`，1/1 通过（2026-09-09）。Master/Daemon 集成测试还验证 `task.create` 经 `POST /extensions/{id}/tasks` 持久化并返回惰性结果，以及扩展禁用后新任务立即返回 409、普通用户返回 403、payload 超限返回 413。远程源的 HTTPS 目录读取已由单元和 Master TLS 场景覆盖，真实浏览器远程源部署与高延迟证书轮换仍未计入通过。

前端 `extension-runtime.test.ts` 覆盖 transport 对 `task.create` 的路径、CSRF、payload 和未知能力拒绝；当前包含 registry 边界在内的 `npm test` 为 6 个测试文件、28/28 通过。
transport 现支持由宿主显式注入 `window.open`、`state.capture`、`state.restore` 回调；未注入时这些方法仍立即拒绝，不会隐式越权。此前定向单元测试为 23/23。
新增认证 `GET /api/v1/extensions/{id}/bundle` 仅返回已启用扩展的已校验包体，禁用后返回 409，前端 `fetchExtensionBundle` 仅使用该 no-store 入口，为 sandbox iframe loader 提供明确边界。此前定向前端单元测试为 24/24。
新增 `ExternalSandboxApp.vue` 与 `loadExternalSandboxApp`：bundle 只在 `sandbox="allow-scripts"` iframe 的 opaque origin 中执行，通过 `postMessage` 接入受限 transport；未知宿主方法仍拒绝。`npm run check && npm test` 通过（24/24）。完整资源标签/状态恢复端到端场景仍未计为通过。
工作区恢复时会扫描已保存的外部 appId，按认证 manifest 动态注册 sandbox host；组件从当前 viewTab 的 resourceRef 解析 nodeId，因此同一扩展可在跨节点资源标签中复用，而不会把节点绑定在首次加载时。
扩展管理窗口对已启用扩展提供“打开”入口，直接走同一动态 sandbox 注册路径；重复打开已注册扩展不会重复注册。
transport 对已加载 manifest 的 `window.open`、`task.create` 能力声明增加本地门禁；单元测试现为 26/26，并覆盖无 nodeId 的总览扩展只能开窗/恢复、不能提交任务。
Sandbox 已将 `window.open`、`state.capture`、`state.restore` 接到真实桌面 store：打开动作返回实际 window/view ID，现场状态按 viewTab 持久化并恢复；无节点的总览扩展仍可开窗，但任务调用会明确拒绝缺少 nodeId。
运行期间每次 bridge 调用都会重新读取当前 viewTab 的 resourceRef；标签切换资源或移窗后，`task.create` 不复用首次加载的旧节点身份。`npm run check && npm test && npm run build` 通过（26/26）。
新增浏览器 E2E 真实加载已启用 bundle：bundle 在 opaque-origin sandbox iframe 中执行 `state.capture`，未列出的宿主方法被拒绝；修复响应式 Vue 状态无法结构化克隆的问题后，通过 `npm run test:e2e -- --workers=1 --trace=off --grep 'enabled extension bundle' --reporter=line`（1/1，3.5s）。

## 2026-09-10 本地 catalog 与真实 bundle 生命周期

`cmd/devfixture` 的受控本地 catalog 现在提供 `fixture.reference` 的 `v1.0.0` 和 `v1.1.0` 两个签名包。真实场景 `web/tests/real/extensions.spec.ts` 在新的 HTTPS fixture `.local/fixture-1866434427` 上 **1/1 通过**：管理员浏览两个版本，安装 v1、升级 v1.1，读取启用 bundle，禁用后 bundle 返回 409，重新启用并刷新，再从扩展管理窗口打开 opaque sandbox，iframe 中实际执行 v1.1.0 payload，最后卸载并保留默认用户数据。

本轮修复了两个边界：升级留下的 `.previous.json` 不再由 `Manager.List` 暴露为第二个安装项，且清单 `appId` 与文件名不一致时读取失败；sandbox bootstrap 改为同源 `/blora-extension-bootstrap.js`，避免生产 CSP 的 inline script 禁止，同时仅在 opaque iframe 内创建 bundle Blob URL。Master CSP 为 `script-src 'self' blob:`，没有开放 inline script 或宿主页面执行。

真实全套 `npm run test:e2e:real -- --workers=1 --trace=off --reporter=line` 同一 fixture **15/15 通过（2.2 分钟）**，其中包含扩展安装、禁用/重启和 bundle 执行。新增远程目录源的 HTTPS 单元与 Master TLS 集成测试：`GOCACHE=/tmp/blora-go-catalog2 go test ./internal/extensions ./internal/master -run 'TestRemoteCatalog|TestExtensionRemoteCatalogAdminAPI|TestExtensionCatalogBrowseAcquireAndUpgrade' -count=1` 退出 0；源只接受 HTTPS、拒绝重定向、限制响应大小和目录条目，安装仍由 Manager 重新核对完整性/签名。版本迁移、资源标签跨设备迁移及跨设备工作区副本仍未覆盖，网络源的长期高延迟/证书轮换也未验收；这些仍属于 E06/E07 的后续条件。
